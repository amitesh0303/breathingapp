# Multi-screen breathing app with session tracking and theme system

This change replaces a single-screen Expo breathing app (one component, three patterns, no persistence) with a full multi-screen application built on expo-router. The revamp adds file-based routing with tab navigation, a theme system with dark/light modes and glassmorphism cards, session history and achievements persisted to AsyncStorage, eight breathing patterns with difficulty ratings, a reanimated concentric-ring breathing visualization, haptic feedback, and an onboarding flow. The architecture moves from a flat component structure to a layered one: contexts for state (theme, settings, session), shared UI primitives (GlassCard, GradientBackground, AnimatedButton, ProgressRing, Typography), breathing-specific components, and screen files under `app/`.

Watch for: the breathing timer uses a 1-second `setInterval` that introduces phase-transition drift over long sessions (confirmed); the `addSession` callback closes over stale `sessions` state so concurrent/rapid session completions can lose data (confirmed); the session-complete overlay blocks interaction but has no escape hatch in infinite-duration mode (confirmed); and `AsyncStorage.clear()` in the reset-data handler wipes all app storage keys including third-party data without scoping to app-owned keys (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The app now boots through a redirect screen (`app/index.jsx`) that checks an AsyncStorage flag and sends the user to either onboarding or the tab navigator. Onboarding is a one-shot screen with fade-in animation and a "Get Started" button. The tab layout hosts four screens: Home (dashboard with streak, quick-start cards, progress summary), Breathe (session screen with pattern selector, timer, animation, and completion modal), Stats (achievements grid and session history list), and Settings (theme toggle, haptics, sound, data reset).

State management is context-based with three providers stacked in the root layout. ThemeContext persists a dark/light preference. SettingsContext persists haptics, sound, and default duration. SessionContext persists an unbounded session history array and derived achievements, recalculating streaks on every `getStats()` call.

The breathing timer is a `setInterval(1000)` loop that counts seconds and advances phases by decrementing `phaseTimeLeft`. Phase transitions happen inside the `setPhaseTimeLeft` updater function. Because the interval isn't tied to wall-clock time, accumulated timer drift means a 10-minute session can be materially longer than 10 real minutes on slow devices or backgrounded apps.

The `addSession` function in `SessionContext` captures `sessions` and `achievements` via closure at the time the callback is memoized. If two sessions complete in the same render cycle (unlikely but possible with rapid unmount/remount) or if the user backgrounds the app and state isn't refreshed, one session's write can overwrite the other's. The stale-closure pattern is a known pitfall with `useCallback` that depends on array state.

<summary>Issues (8)</summary>

1. **Timer drift on long sessions** — The 1-second `setInterval` in `breathe.jsx` accumulates drift because it doesn't anchor to wall-clock time. Replace with a `requestAnimationFrame` loop or periodically reconcile against `Date.now()`.
2. **Stale closure in addSession** — `addSession` in `SessionContext` closes over the `sessions` array snapshot. Use a functional updater (`setSessions(prev => [...prev, newSession])`) and derive achievements from the updated list inside the updater, or use a ref.
3. **No escape from infinite-mode completion overlay** — When `selectedDuration === 0` (infinite mode), there is no way to end the session and trigger the completion flow, since the `sessionComplete` flag is only set when `totalElapsed >= selectedDuration` and `selectedDuration > 0`. Add a manual "end session" action that records partial sessions.
4. **AsyncStorage.clear() nukes all keys** — The reset handler in `settings.jsx` calls `AsyncStorage.clear()` which removes every key in the store, not just app-owned ones. Use `multiRemove` with the known key list instead.
5. **StatusBar hardcoded to light** — The root layout sets `<StatusBar style="light" />` regardless of the selected theme. In light mode this makes the status bar invisible against a light background.
6. **GradientBackground particles ignore theme changes** — Particle colors are captured in a `useRef` on first render and never update when the theme toggles, leaving stale-themed particles on screen after switching modes.
7. **Unbounded session history growth** — `SessionContext` loads and saves the entire session array every time. With months of daily use this array grows without bound, eventually slowing AsyncStorage reads and increasing memory pressure. Consider pagination or archiving old sessions.
8. **Achievement definitions duplicated** — The achievement list is defined identically in `SessionContext.jsx` and `stats.jsx`. Extract to a shared constants file to prevent drift.

## Breathing timer phase logic and drift

The core timer in `breathe.jsx` runs a `setInterval` at 1000ms intervals. Each tick decrements `phaseTimeLeft`; when it hits zero, the phase advances. This approach measures time in "ticks elapsed" rather than wall-clock time, so if a tick fires late (GC pause, background tab throttling, JS thread contention on a loaded device), the error accumulates. Over a 10-minute session that's 600 ticks, even 5-10ms average drift per tick adds up to several seconds.

More critically, the `setPhaseTimeLeft` updater function performs the phase-transition side effect (calling `setCurrentPhase`) from inside a state updater. While React doesn't forbid this, it couples phase transitions to the batching behavior of `setInterval` callbacks in React 19's concurrent mode. If two ticks batch, the second tick's updater sees the already-decremented value and may skip a phase boundary.

```jsx
setPhaseTimeLeft((prev) => {
  if (prev <= 1) {
    // Side effect inside updater: sets phase state
    phaseIndexRef.current = (phaseIndexRef.current + 1) % activePhases.length;
    const nextPhase = activePhases[phaseIndexRef.current];
    setCurrentPhase(nextPhase); // <-- state set inside another setter's updater
    phaseTimerRef.current = pattern[nextPhase];
    return pattern[nextPhase];
  }
  return prev - 1;
});
```

The fix is to anchor the timer to `Date.now()` at session start, compute elapsed time on each tick, and derive the current phase deterministically from elapsed time and the pattern's cycle length.

## Stale closure in SessionContext.addSession

`addSession` is wrapped in `useCallback([sessions, achievements])`. When it executes, it spreads the captured `sessions` array:

```jsx
const updatedSessions = [...sessions, newSession];
```

If React hasn't re-rendered the provider between two calls to `addSession` (e.g., rapid double-tap of a "complete" button, or a race between the `useEffect` that detects completion and a manual stop), the second call spreads the same stale `sessions` and the first session is lost. The standard fix is `setSessions(prev => [...prev, newSession])` and computing achievements from the new list returned by the updater.

## Infinite-mode session has no completion path

When the user selects the infinity duration option (`selectedDuration = 0`), the completion check in the `useEffect` is gated by `selectedDuration > 0`:

```jsx
if (selectedDuration > 0 && totalElapsed >= selectedDuration && playing) {
  setPlaying(false);
  setSessionComplete(true);
  addSession({ ... });
}
```

This means in infinite mode, pressing pause stops the timer but the session is never recorded. There's no "finish" button exposed in the paused-infinite state. The user's breathing time is lost. Either the pause button should become a "finish session" button after some minimum elapsed time, or a separate "end session" action should be available.

## AsyncStorage.clear() scope

In `settings.jsx`, the "Reset All Data" handler calls:

```jsx
await AsyncStorage.clear();
```

`AsyncStorage.clear()` removes every key in the store, not just the app's `@session_history`, `@achievements`, `@theme_preference`, `@settings`, and `@onboarding_complete` keys. If any third-party library (analytics, crash reporting, Expo internal state) persists to AsyncStorage, those keys vanish too. Replace with `AsyncStorage.multiRemove(['@session_history', '@achievements', '@theme_preference', '@settings', '@onboarding_complete'])`.

## StatusBar ignores theme selection

The root layout hardcodes:

```jsx
<StatusBar style="light" />
```

When the user switches to light mode, the status bar text remains white on a light background, making it unreadable. Since `_layout.jsx` renders the `StatusBar` inside the `ThemeProvider` scope (providers wrap the children), a nested component could read the theme. The simplest fix is to extract the `Stack` and `StatusBar` into a child component that calls `useTheme()` and sets `style={isDark ? 'light' : 'dark'}`.

## GradientBackground particle colors frozen at mount time

`GradientBackground` captures particle configuration in a `useRef`:

```jsx
const particles = useRef(
  Array.from({ length: NUM_PARTICLES }, (_, i) => ({
    ...
    color: i % 2 === 0 ? theme.colors.primary : theme.colors.accent,
  }))
).current;
```

Because `useRef` persists across renders and the initializer only runs once, toggling from dark to light theme doesn't update particle colors. The particles remain teal/purple on a light cream background. Replace with `useMemo` keyed on `theme.isDark` to regenerate particle configs on theme change.

## Achievement definition duplication

The `ACHIEVEMENT_DEFINITIONS` array is defined identically in both `SessionContext.jsx` (lines 8-18) and `stats.jsx` (the `allAchievements` const). If a new achievement is added to one and not the other, the stats screen will show stale data or miss rendering new badges. Extract to a shared file under `src/constants/achievements.js`.
